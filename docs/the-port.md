# The port: how the recompiled game runs on a PC

This document explains how the Windows executables are produced from the
cartridge and how they run: static recompilation with ndsrecomp,
the dispatch seam the port uses to change the game, the safe ways to call the
game's own functions, the shell that replaces the framework's frontend, the
framework patches, BIOS and firmware, saves and settings, the Bounty Hunter
build's features, and how all of it is verified.

Every address is a guest address in the USA cartridge
(SHA-1 `7c1afa070797945ba5a2577c7ddfded5cf2fc443`). The game's own
architecture is in [game-internals.md](game-internals.md), and its networking
in [multiplayer.md](multiplayer.md).

## Two builds, one binary

`port/build.sh` produces one executable and copies it under two names. The
name chosen picks the build:

| executable | build | what it is |
|---|---|---|
| `lsw2.exe` | base | the game as shipped, with its own save; the reference everything else is measured against |
| `lsw2_bountyhunter.exe` | Bounty Hunter | the arena as a game of its own: everything unlocked, an online lobby, host rules, 2-4 players over the internet |

`main()` works the build out from `argv[0]` and sets `LSW2_FORK=1` for the
Bounty Hunter build before anything else runs, so code that runs before the
shell exists (the override registration) can still tell the two apart. The
rule between them, stated in `port/ARCHITECTURE.md`: the base build owns
fidelity, and the Bounty Hunter build owns content. An enhancement may change
what the player sees. When it must change what the game computes, it is a
named, ROM-gated title patch.

## Static recompilation with ndsrecomp

The port is built on [ndsrecomp](https://github.com/RetroPortingToolKit/ndsrecomp),
a DS static-recompilation framework derived from melonDS. Its recompiler
translates ARM and Thumb machine code into C ahead of time. Its runtime
supplies the rest of the DS (bus, scheduler, DMA, timers, 2D and 3D GPU,
sound, wireless) and an ARM interpreter as a fallback.

### Four programs, and their entry points

The DS boots two CPUs, but the code that runs lives in four places, and only
the first two appear in the ROM header:

| bank | region | entry points | how its base was found |
|---|---|---|---|
| `lsw2_arm9` | ARM9 main code, autoload section 0, `0x02000000` | 7,518 | ROM header (the ARM9 image is BLZ-compressed; it unpacks to 0x107238 bytes in three autoload sections) |
| `lsw2_arm9_itcm` | ITCM, `0x01FF8000`, the ARM9's hottest routines | 72 | autoload section 1 |
| `lsw2_arm7` | cartridge ARM7, `0x02380000` | 930 | ROM header |
| `lsw2_arm7_wram` | the block the ARM7 copies into WRAM, `0x037F8000` | 3,358 | measured, by sliding `arm7.bin` against a console memory snapshot until the bytes matched (from `arm7.bin + 0x1B0`) |

The entry points are published in `port/lift/*.toml`: an address, an
instruction mode, and a name (`FUN_xxxxxxxx`). They are generated by
`tools/gen_ndsrecomp_config.py` from a Ghidra analysis of the cartridge. That
analysis is decompiled game code and is not part of the public source; the
configs it yields are only addresses, modes and names, so a checkout without
it builds from the published lists. The **mode is derived from the instruction
bytes**, not taken from Ghidra. Candidates whose mode cannot be established are
left out, and most of those turn out to be string tables and pointer arrays.

The recompiler follows calls from those seeds, and the build lifts roughly
44,000 functions in all. The two code regions that nothing in the header
describes mattered most: before the WRAM copy was banked, the ARM7 interpreted
about 790 times as many instructions as the ARM9.

### Banks and shards

Each program is emitted as a **bank**: a dispatch table from guest address to
host function, plus the bodies. Bodies are split into **shards**, separate C
files, because the ARM9 bank unsharded is a single 242 MB translation unit.
The ARM9 bank has 48 shards, the ARM7 8, the WRAM copy 4 and the ITCM 2, all
with stable address-based shard boundaries. The build emits into a staging
directory and copies only files whose contents changed, so editing the shell
does not recompile 33,000 lifted functions.

A lifted function is `void lsw2_arm9_FUN_xxxxxxxx(void)`. Its arguments and
results live in the emulated register file `g_cpu.R[]`. Inside one shard, a
`BL` to another lifted function compiles to a **direct C call**. A branch that
leaves the shard, or whose target is computed (a `BX`, a `POP {pc}`, a vtable
call), goes through `runtime_dispatch(pc)`. That one fact decides where the
port can intervene (see "Dispatch overrides").

### Live-byte validation

The ITCM and ARM7 WRAM banks are emitted with `--validate-live-bytes`. That
code is copied into RAM at runtime, so before dispatching to compiled code the
runtime checks that the bytes now at that address still match the bytes that
were lifted. Dispatching on the address alone would trust code that may not
be there yet. The cartridge banks are immutable and need no check.

### The interpreter fallback

`runtime_dispatch` looks the target up in the registered tables. If no table
holds it and the target is code that was written into RAM at runtime (the bus
tracks write provenance; the game's code itself was loaded into RAM), the
runtime runs the **guest's own instructions** through its interpreter
("Tier 3"). An untranslated function therefore degrades to *slow*, never to
*wrong*. That is the main reason the port uses ndsrecomp rather than compiling
decompiler output, which has produced several distinct classes of silent
mistranslation. A target with no table entry and no provenance is a **dispatch
miss**: the CPU halts, and the port writes the PC, LR, registers and pending
guest returns to `dispatch_misses.log`.

The interpreter gap is closed with runtime evidence. The runner records every
address that fell through to the interpreter (a coverage manifest), and
`tools/coverage_to_entrypoints.py` turns those into extra entry points. A
coverage address is where interpretation *started*, often mid-function, so
each is checked before it is promoted. One hot case was a mis-cut function:
Ghidra had started `FUN_01FFAD3C` four bytes late (the real first instruction
at `0x01FFAD38` is a `push {r0-r3}`). Every per-actor call entered the gap and
was interpreted, about 39% of all interpreter entries.
`tools/ghidra_scripts/RebaseFunctionEntry.java` fixes such a function in place.
Today the interpreter is a negligible share of the game thread. What remains
is mostly ARM7 delay loops in an unlifted section.

Compiled code still does per-instruction work: every generated instruction
updates the cycle clock and checks `runtime_should_yield()`, the preemption
point that lets the scheduler interleave the two CPUs and service events.
Forcing those helpers inline was tried, was exact, and saved nothing
measurable, so it was reverted.

## Dispatch overrides

The port changes game behaviour by registering its own C function for a guest
address. Every override lives in `port/frontend/dispatch_overrides.cpp` or a
module it calls. The lifted body stays linked, so an override that proves
wrong is a switch away from being disabled.

```c
struct NdsDispatchEntry { uint32_t addr; ...; void (*fn)(); ... };
```

Registration happens from a hook in the runner's `main()`, **before** the title
banks are registered, because lookup answers with the first table that holds
an address. The tables are:

| table | installed | purpose |
|---|---|---|
| `kVwhOverrides` | Bounty Hunter, unless `LSW2_VWH=0` | the host-level wireless layer; first, so it wins over older hooks on the same methods |
| `kOverridesAlways` | both builds | observers and fixes that the base game needs too (state-request logging, head reveal, the null-manager guard on `0x0206EF0C`) |
| `kOverridesCore` | Bounty Hunter (or `LSW2_HLE=1`) | the build's features |

Each table is **sorted at registration**, because the runtime binary-searches
it. Unsorted tables once made overrides fire or not depending on unrelated
entries: adding one element moved the search's midpoints.

An override either does the whole job and returns the way a lifted function
does (`R[15] = R[14]`), or it adjusts state and **tail-calls** the lifted
original by setting `R[15]` to it with `R[14]` left as the caller's return.

### What makes an override safe

Each of these rules was learned from an override that registered cleanly and
then never ran, or ran and broke something.

1. **It must be reached through dispatch.** A call from the same shard is a
   direct C call and never consults the table. An override on such a target
   is legal, silent and inert. Prefer functions with **zero direct callers**:
   vtable methods, callbacks, or functions whose callers sit in other shards.
   `tools/sweep_override_reachable.py` checks every registered address against
   the generated code. The receive pump `0x020B0410` is a good host for this
   reason: its one caller is in a different shard.
2. **It replaces the function for every caller.** An override takes
   responsibility for all of a function's callers, not just the one the design
   was about. `0x020B111C` has eight, and the state requester `0x0205ECC4` has
   176. `tools/sweep_override_targets.py` lists them before any design is
   written.
3. **The address must be an entry the lifter emitted.** An address one
   instruction into a function, inside a literal pool, or inside a range a
   config declares as data never reaches a table.
   `tools/sweep_guest_addresses.py` checks every call target and override row.
4. **The lifted original is called once, as the last act.** A lifted function
   can be suspended partway (a slice yield) and return to C early. Code placed
   after it in an override runs at the wrong time, so an override that needs
   two guest calls cannot make both. The port patches an interpreted `BL`
   instead, or takes the second step on a later frame.
5. **`lr` names only a direct caller.** An override that recognises its caller
   by return address works only if that caller calls it directly. A wrapper in
   between moves `lr`. `tools/sweep_lr_checks.py` checks that every `lr ==`
   constant names a real call site of the overridden function.
6. **Prefer observing to replacing.** Many overrides log or adjust one value
   and then tail-call the cartridge's own function, so the game's code still
   does the game's work.

The dispatcher histogram (framework patch 0010) counts the PCs dispatch is
actually asked about. That is exactly the set an override can hook, and it is
cheaper to measure than to guess.

## Calling the game's own functions

The port prefers to make the **game** do things: request a state, send a
message, apply a part. There are three ways, and one way that looks
reasonable and is wrong.

### Writing the game's data

The cheapest route needs no call at all. A state change is a request record
the state manager's pump reads every frame. The port writes it exactly as
`0x0205EC4C` would, into the screen or world slot's block and without the
status byte, and the manager does the rest: it fades the slot, runs the old
state's exit and destructor, then builds the new state. A message can likewise
be delivered by writing an entry into the receive ring with a new sequence
number (`port/frontend/netmsg.h`). Every side effect is then the cartridge's
own code running in its own order.

### `lsw2_guest_call`: a host call between frames

`port/frontend/guestcall.cpp` calls a lifted function from the per-frame
"fork tick", which runs between frames with the guest settled:

```c
save the whole CPU state
g_cpu.R[14] = synthetic_return;  g_cpu.R[15] = target;
runtime_call_push_return(synthetic_return);
lsw2_arm9_FUN_<target>();
if (g_cpu.R[15] != synthetic_return) runtime_call_cancel_return(...);
restore the whole CPU state
```

It passes up to four registers and two stack words. Every push is matched,
because the return stack aborts the process on overflow. It has hard limits.
Between frames nothing is scheduled: no VBlank, no timer, no device event. So
a function that **waits for an interrupt** or **starts a DMA transfer** never
returns. And while the guest is halted waiting for VBlank, the first
`runtime_should_yield()` refuses the call before its first instruction.
`lsw2_guest_ready()` reports whether a call can be attempted right now.
`tools/sweep_guestcall_safety.py` flags targets that poll in a loop: the
wireless session end `0x020B111C` reaches `WH_End` and polls it in a
`do…while`, so it can never be called this way.

### The gear hop: running a call on the guest's own thread

For everything else the port uses the **hop** (`port/frontend/gearhop.cpp`).
It is named after its first use, the gear applier `0x020063D4`. Requests go
into a queue. A *host* override, one that is dispatched every frame such as
the component update `0x0202C218` or the HUD's frame step `0x0208CDB0`, checks
the queue on entry. When a request is waiting, the host saves `r0-r3` and
`lr`, sets `R[14]` to its own entry address and `R[15]` to the target, and
returns. The guest then runs the target **inside its own frame**, with the
scheduler live and interrupts firing. When the target returns, it lands on the
host's address. The dispatcher calls the override again, which recognises the
return, restores the saved registers, and does its normal job.

A request can be **pinned to one host**, so it runs at the point in the frame
where the game itself would run it. That matters. Deleting HUD sprites from
the middle of the entity update pass, rather than inside the HUD's own step
where the cartridge deletes them, left a use-after-free that only showed
under a busy heap. The hop now serves the gear applier, the party and HUD
portrait refresh, the Extras toggle, the game's message send `0x020B04F0`,
the player-action helpers (the customize hat/weapon calls), and `WH_End`.

### Never call lifted code directly from host code

Calling `lsw2_arm9_FUN_xxxxxxxx()` straight from the tick looks like it should
work, and it fails in a confusing way. A lifted function's entry dispatches on
the **active CPU's** `R[15]`, and between frames the active CPU may be the
ARM7. A session-end path that called the lifted `WH_End` (`0x020ADD78`) this
way ran ARM9 code against the ARM7's state, missed dispatch at an ARM7 BIOS
address, and halted that CPU, which is a crash. It is now a hop. The rule:
host code reaches guest code only through `lsw2_guest_call` (which saves and
sets up the CPU) or the hop.

## The shell

The framework's runner is one executable whose `main()` does all the setup
(command line, config, ROM, BIOS, bank registration, direct boot) and then
calls a frontend function that owns the SDL windows and the present loop and
exposes no hooks. The port **links every runner object except
`frontend.cpp`** and supplies its own `port/frontend/frontend.cpp`. It keeps all
of the setup and owns the loop. This is the same split Ship of Harkinian makes
with libultraship: the framework core is a library, and the shell is the
port's.

What the shell adds:

- **Presentation.** Both screens, side by side or with the touch screen as a
  floating panel inside the main window. Scaling preserves aspect. The
  framework's OpenGL 4.3 compute renderer is presented by the shell itself
  (`glpresent.cpp`), with 1x-4x internal resolution and xBR texture
  upscaling, and the software rasteriser as a fallback.
- **Pacing.** 60 fps, clocked by audio consumption at the mixer's exact
  32,728 Hz. The game itself simulates at 30 Hz.
- **Adaptive widescreen.** Off by default, and a title patch rather than a
  presentation setting. The 3D raster widens to the window. The compute
  renderer accepts only widths in steps of 64 pixels, so on a 16:9 display
  the width snaps to 320 rather than failing over to software. The game's
  own actor visibility test still uses the original 256-pixel bounds, so
  actors near the new edges can pop in and out, and the Video tab says so.
  2D layers stay native during gameplay, except one named BG that a
  full-screen film effect blends over the 3D.
- **The settings menu** (imgui, Esc or F1): video, input, touch, a debug tab,
  a cheats tab (base build only, nothing applied unless pressed), and
  multiplayer (player name, master-server address).
- **Input.** Keyboard and gamepad, rebindable, saved by action name.
- **The Bounty Hunter build's in-game menus.** The host settings, the lobby
  console, the join and lobby lists, and the popups are drawn in the game's
  style, with the game's own fonts exported from your ROM, and composited into
  the DS frame (`gamemenu_render.cpp`, `gamefont.cpp`).
- **Instances.** `--instance N` runs another copy with its own save, settings
  and ports, which is how multiplayer is tested on one machine.

The **fork tick** is the shell's per-frame hook into the game. It runs between
two guest frames and is where most Bounty Hunter features live. Under online
lockstep it must not change simulation state (see
[multiplayer.md](multiplayer.md#the-lockstep-rule)).

## Framework patches (`port/patches/`)

The framework is a pinned dependency fetched by `tools/fetch_ndsrecomp.sh`.
The port's changes to it are numbered patches that `port/build.sh` applies,
skipping any already present. Grouped by purpose:

| purpose | patches |
|---|---|
| presentation | 0001 (widened 2D backgrounds, and named BGs extended across the full width), 0002 (compute host: viewport sub-rect, deferred swap so the shell can draw its UI on top), 0016 (hide named BG layers from one engine's picture, presentation only), 0018 (backdrop mask), 0020 (texture-palette halfword access) |
| launch | 0005 (standalone launch with no arguments, the fork flag, FreeBIOS when no dumps), 0021 (first-run ROM request) |
| instruments | 0003 (debug surface `write_mem`), 0004 (debug pump request/response pairing), 0006 (input record and replay), 0007 (unmapped accesses name their PC and guest call stack), 0009 (write watch names the writer), 0010 (dispatch histogram), 0017 (dispatch misses record how they got there), 0019 (read-only view of cartridge bytes) |
| correctness | 0011 (advance time past a zero-debt GXFIFO stall, which otherwise deadlocks), 0015 (ARM9 DMA bypasses the TCMs, as on hardware) |
| local wireless | 0008 (frame counts), 0012 (bridge frames skip the RF channel match), 0013 (tunable CPU interleave, `LSW2_ITERCAP`), 0014 (event-driven waits and client pacing) |

Patch 0015 is a good example of a framework fix found through the game. With
four players in Game Settings, a VBlank VRAM upload with a null-based
destination (`0x00010400`, which mirrors ITCM) wiped 2.5 KB of ITCM code. On
hardware, DMA cannot see the TCMs and the same transfer writes nothing.

## BIOS, firmware, first run

**BIOS.** The executables embed **FreeBIOS** (BSD-2-Clause). Your own
`biosnds9.rom` and `biosnds7.rom` in `port/bios/` are used instead when present,
and are checked against the framework's SHA-1. On an identical 400M-cycle
boot path, FreeBIOS reached the same ARM9 PC (`0x020CEA8C`) as retail dumps,
with dispatch counts within about 1%. *Building* still needs the retail dumps,
because the runner's bank target always links banks recompiled from them.

**Firmware.** No firmware dump is used. The framework's firmware RAM banks
were captured against one specific image, and a dump from another console does
not match it. The build sets `NDS_BOOTSTRAP_FIRMWARE=ON`, the runner synthesises
firmware (`generated_firmware = true`), and `boot = "direct"` skips the boot
menu. The DS user-settings block that firmware leaves at `0x027FFC80` matters
to the game: its wireless layer reads the nickname (ten UTF-16 units at `+0x06`,
length at `+0x1A`) for the beacon, the browse list and the peer names. The port
writes the player's chosen name there in both builds (`dsname.cpp`).

**First run.** Patch 0021 replaces a console message that closed with its
window. With no matching ROM in `rom/`, the game shows a message box and a
file picker, verifies the chosen dump's SHA-1 against `game.toml`, and copies
it into `rom/`. The guest reads its assets straight from the cartridge, so no
extraction step is needed to play.

## Saves and settings

**The cartridge save** is a 512-byte EEPROM (`save_type = "eeprom-tiny"` in
`port/game.toml`). melonDS's ROM database lists the game as save type 1. The
game probes the chip at boot and stops with "could not detect DS data" if it
is missing, so the device stays even though the Bounty Hunter build persists
nothing meaningful through it. The two builds keep separate files
(`baseline.sav`, `bountyhunter.sav`). A new Bounty Hunter save is seeded from an
unlocked template.

**Everything unlocked** is applied at runtime, not by patching checks. Once the
lobby has settled (the flag block is filled from the save during the load,
so an earlier write would be overwritten), `lsw2_cheats_unlock_everything()`
sets the owned and seen flags for every character and vehicle, the bought
flags for all 22 Cantina terminal Extras, and the customization parts and
weapons. The flag accessors are `0x02086534` / `0x02086458` (test/set at
`block + 0x44CC`) and their twins at `+0x44DC`, with block `0x02104D90`. Extras
*enabled* (`+0x4518`) is left alone, because it belongs to the host's match
rules.

**Settings** are one flat JSON file, written as a key-value store
(`settings_store.cpp`). Every key is loaded, the known ones are overlaid, and
the whole map is written back atomically. A key one build does not know (the
base build has no Multiplayer tab) survives the other build's save, and one
malformed value is skipped rather than fatal. An old `key=value` file is
imported once.

Each feature is built on a mechanism the game already has, wherever one
exists.

## How it is verified

The port is checked by measurement against the running game, not by reading
code alone. A good number of plausible readings in this project turned out
wrong once measured.

### The debug surface

Each running instance serves a local debug socket on `127.0.0.1:19842`
(instance N: `19842 + N - 1`). Through it a script can read and write guest
memory, take screenshots of each screen, inject input, and query state, all
without touching a window. `tools/drive_session.py` drives a session step by
step and prints the new `[state]` log lines after each step, pairing "what I
just did" with "which state the game requested". Instruments switched on by
environment variables:

| variable | what it reports |
|---|---|
| `LSW2_PRESENT_SHOT` | the frame actually presented (the screen composited by the shell, which a framebuffer read cannot see) |
| `LSW2_WRITE_WATCH=<addr>` (`_VALUE`, `_STACK`) | every guest store to an address: PC, LR, registers, guest call stack |
| `LSW2_BUS_WARN_STACK=1` | the guest call stack behind the first unmapped accesses |
| `LSW2_WH_TRACE`, `LSW2_RNG_TRACE`, `LSW2_STATE_TRACE` | wireless calls, RNG draws per dataset, per-actor state hashes per dataset; two consoles diff by dataset index |
| `--record` / `--replay` | input recording and replay |
| `LSW2_COUNTS_AT=f1,f2,...` | the exactness gate (below) |

A logged state change is not a rendered frame. Results are judged by
presented frames and by counts, never by a log line alone.

### The exactness gate

An offline boot is **bit-reproducible**: the framework's real-time clock is a
fixed date, so even the RNG seed repeats. `LSW2_COUNTS_AT` prints, at the
listed host frames, the guest cycle clock, both CPUs' retired-instruction
counts, and an FNV-1a hash of all 4 MB of main RAM. Two builds that print the
same lines computed exactly the same thing. A change meant to be
behaviour-neutral, such as a performance change or a refactor of an override,
is graded against this gate before anything else is measured.

### Unit tests and sweeps

`tools/run_unit_tests.sh` runs at the end of every build (about 70 entries).
The C++ tests cover the shell's and the networking's pure logic and need no
ROM: the lockstep session with four stations in one process, the transport
over loopback, the host settings, menus and timers. The tests report three
outcomes, because a test that cannot reach the master server is neither a pass
nor a failure.

The **sweeps** are Python checks over the source and the generated code. Each
one exists because its failure shape shipped at least once:

| sweep | the question |
|---|---|
| `sweep_override_reachable` | does dispatch ever consult this override's address, or do direct calls bypass it? |
| `sweep_override_targets` | who else calls a function the port replaces? |
| `sweep_guest_addresses` | is every call target and override row a real function entry? |
| `sweep_guestcall_safety` | can this function be called from the host, or does it poll forever? |
| `sweep_lr_checks` | does every `lr ==` test name a direct call site? |
| `sweep_orphans`, `sweep_call_reachable`, `sweep_test_only` | is each port function called by shipping code, through a live chain, by more than its own test? |
