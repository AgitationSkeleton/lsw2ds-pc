# The save file, and how scope 4 is delivered

LSW2's cartridge save is a **512-byte EEPROM** (`eeprom-tiny`), identified from
melonDS's ROM database — entry `{0x45374C41, 0x02000000, 0x00000001}`, game code
`AL7E`, ROM size 32 MB matching this cartridge exactly, SaveMemType 1, which
`NDSCart/CartRetail.cpp` resolves through `sramlengths[1] = 512` and
`case 1: SRAMType = 1; // EEPROM, small`.

Both files here begin `LEGO000D`.

## What "all unlocked" actually costs

Measured, not guessed. A **virgin** save was generated by running the port with
a fresh save path and letting the game create one, then compared byte for byte
against `unlocked-template.sav` (captured from a session with the unlock codes
entered at the Cantina):

**95 of 512 bytes differ.** The interesting runs:

| offset | bytes | virgin | unlocked | what it looks like |
|---|---|---|---|---|
| `0x07E–0x0A6` | 41 | all `00` | all `FF` | **the main unlock bitfield** — 328 bits, comfortably more than the roster plus extras plus editor parts |
| `0x064–0x06C` | 9 | all `00` | `ff ff f7 bf ff df 7d fd ff` | a second flag block, only partly set — note the gaps |
| `0x06E–0x070` | 3 | `00 00 00` | `a0 ff 0f` | |
| `0x04A–0x05C` | 19 | all `00` | `08 90 41 b2 fa 1a` ×3 | three identical 6-byte records — character-editor slots |
| `0x0B1–0x0B4` | 4 | `00000000` | `15 cd 5b 07` | `0x075BCD15` = **123,456,789** studs, from the cheat |
| `0x0BE–0x0BF` | 2 | `96 a7` | `cd 01` | checksum |

The 41-byte run of `FF` is the part scope 4 actually needs. The stud value is
incidental — a side effect of how the template was captured, and harmless, since
scope 4 says currency should not gate anything and 123 million does not.

**The second block is only partly set**, which is worth noticing rather than
smoothing over: `f7`, `bf`, `df`, `7d`, `fd` all have bits clear. Whatever those
flags are, "enter every unlock cheat" did not set all of them. If something turns
out to be missing in-game, this is where to look first.

## Why this is the right layer

The requirement is that everything is available from the start. The tempting
implementation is to find the game's unlock checks and defeat them. This is
cheaper and strictly safer: hand the game a save in which the work is already
done, and change **nothing else**. No game logic is touched, so nothing
downstream can diverge from the cartridge because of it.

The first attempt at scope 4 removed the save *device* (`save_type = "none"`) on
the reasoning that "no save system" meant no save hardware. The game refused to
boot — *"could not detect DS data"*. The chip is hardware the cartridge
specifies; the unlocks are content. See `port/ARCHITECTURE.md`.

## Behaviour

`port/run.sh` copies the template to the save path **only when no save exists**.
It never overwrites progress. `port/run.sh --fresh` deletes the save and reseeds
deliberately.

The virgin save is kept out of the repo — it is reproducible in one command:

```sh
nds_runner.exe <bios> 900000000 --rom <rom> --save-path virgin.sav \
    --boot direct --generated-firmware
```
